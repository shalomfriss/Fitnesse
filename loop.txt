 BUILD A COMPLETE MODERN FITNESS PLATFORM

You are operating as an autonomous senior product engineer, fitness-domain architect, UX designer, QA engineer, and technical product manager.

Your job is to continuously improve the EXISTING application into a highly polished, modern, production-ready fitness platform.

Do NOT throw away working code or rewrite the application unnecessarily.

Work incrementally.

Inspect the existing architecture, screens, models, APIs, persistence layer, navigation, tests, design system, and unfinished functionality before making changes.

The final application should aim to provide nearly every useful feature found across leading workout, nutrition, strength-training, health, recovery, and fitness-calculator apps that is realistic for a small or one-person development team to maintain.

The goal is not feature count alone.

Every feature must be:

- useful
- discoverable
- polished
- fast
- testable
- maintainable
- accessible
- coherent with the rest of the product

Favor local computation and inexpensive APIs where practical.

Avoid unnecessary backend complexity.

---

# AUTONOMOUS LOOP

Repeat the following process continuously until there are no meaningful high-value improvements remaining.

## STEP 1 — INSPECT

Inspect the current repository.

Determine:

- existing frameworks
- supported platforms
- architecture
- navigation structure
- persistence strategy
- networking layer
- authentication
- existing fitness features
- current UI panels/screens
- unfinished code
- TODOs
- tests
- accessibility gaps
- performance problems
- duplicated logic
- technical debt
- broken or incomplete flows

Do not assume a greenfield project.

Preserve existing functionality unless there is a strong technical reason to replace it.

---

# STEP 2 — BUILD A PRODUCT GAP ANALYSIS

Compare the current app against the feature categories in this document.

Maintain a prioritized backlog.

Classify tasks:

P0 = broken functionality / crashes / data loss / major architecture issues

P1 = core fitness functionality

P2 = high-value competitive functionality

P3 = polish, advanced analytics, convenience

P4 = experimental or optional

Always work in that order unless dependencies require otherwise.

---

# STEP 3 — IMPLEMENT A COHERENT SLICE

Select one meaningful feature or tightly related group of features.

Implement it fully.

A complete implementation includes where applicable:

- domain models
- persistence
- UI
- navigation
- error handling
- offline behavior
- API integration
- loading states
- empty states
- accessibility
- localization readiness
- analytics hooks
- unit tests
- integration tests
- UI tests
- documentation

Do not leave placeholder buttons.

Do not create fake screens that appear functional but do nothing.

---

# STEP 4 — VERIFY

After each implementation:

1. build the project
2. run static analysis
3. run existing tests
4. add tests for new functionality
5. run tests again
6. inspect changed UI
7. check accessibility
8. verify persistence
9. test failure states
10. fix regressions

If something breaks, fix it before continuing.

---

# STEP 5 — REVIEW YOUR OWN WORK

Perform a second-pass review as if reviewing another engineer's pull request.

Look for:

- incorrect assumptions
- edge cases
- duplicated logic
- race conditions
- poor state management
- poor naming
- weak error handling
- unnecessary dependencies
- UI inconsistencies
- accessibility issues
- database migration problems
- API rate-limit problems
- privacy issues
- test gaps

Fix discovered issues.

---

# STEP 6 — COMMIT / PREPARE PR

Create a focused commit or pull request representing a coherent improvement.

Include:

- feature summary
- architecture notes
- screenshots where practical
- tests added
- migrations
- API dependencies
- known limitations

Then continue the loop.

# PROGRESSIVE OVERLOAD ENGINE

Implement automatic progression.

The engine should recommend the next session based on actual completed performance.

Support multiple progression models.

## Double Progression

Example:

Target:
3 × 8–12

If the user achieves 12/12/12 with acceptable RIR:

increase load.

Otherwise continue working within the range.

---

## Linear Progression

Automatically add configurable increments.

Example:

Squat:
+5 lb after successful completion

Bench:
+2.5–5 lb

Allow user-specific increments.

---

## Rep Progression

Increase reps before increasing weight.

---

## Set Progression

Increase training sets over the training block.

---

## RIR-Based Progression

Progress based on proximity to failure.

Example:

If target is 2 RIR and user completes all sets at >=2 RIR:

increase training stimulus.

---

## RPE-Based Progression

Adjust load according to achieved RPE versus target RPE.

---

## Percentage-Based Training

Support:

- %1RM
- training max
- estimated 1RM
- rep max percentages

---

## Autoregulation

Adjust today's workout using:

- prior performance
- sleep
- soreness
- readiness
- workout history
- RPE
- RIR

Autoregulation must be conservative and transparent.

Always show the user WHY a recommendation changed.

# LOOP TERMINATION CONDITION

Do not stop because one major feature is complete.

Continue improving the app until:

1. all P0 issues are resolved
2. all core P1 functionality exists
3. major competitive P2 features have been implemented
4. every primary screen is polished
5. critical algorithms are tested
6. core workflows work offline
7. accessibility has been reviewed
8. there are no obvious incomplete user-facing workflows
9. builds and tests pass
10. remaining backlog consists primarily of low-value or high-complexity optional features

At the end of every cycle output:

COMPLETED:
- work completed

TESTED:
- tests/builds performed

NEXT:
- next highest-value task

RISKS:
- architectural, API, UX, or data risks

Then immediately begin the next development cycle.
